# playbook-regression

Playbook regression check. Goal: when a playbook's text changed, prove the new text still produces the same findings on an input it already handled. Read-only: nothing leaves the machine; no file outside `{{paths.reports}}` and your scratchpad is written.

1. Changed playbooks are listed one name per line in `{{paths.automationState}}/playbook-changed.txt` (written by the precheck; `playbook-sha.txt` already holds the new shas). Skip `playbook-regression` itself and `eval-weekly`. If the list is empty or only contains those, write a one-line report saying so and stop.
2. For each remaining playbook `<name>`: pick the most recent `{{paths.reports}}/<name>-*.md` (`ls -t`). None → note "no prior report" and move on.
3. Read the old report in full. Extract the input it worked on: the PR(s) `<repo>#<n>` with head sha, the ticket ids, or for `cleanup` the terminal and worktree lists. Re-run `{{paths.playbooks}}/<name>.md` on exactly that input, following its steps, with these overrides: read only. No `gh api -X POST/PATCH`, no `terminal close`, no `worktree rm`, no chat or ticket writes, no appending to any state file, and no `worker_done` for the inner run. When the input is gone (PR merged with a new head, ticket closed), use the PR at the old head sha when GitHub still serves it, otherwise record "input no longer available" and move on.
4. Compare with the old report: every section the playbook's "Report format" requires (present in old, present in new); findings or items (same set, added, dropped, verdict changed); drafts that changed meaning. Ignore timestamps, ordering and wording.
5. Report, one `## <name>` section per playbook: old report path, input used, a table `section | old | new | same?`, a table `finding | old | new | note` for every added, dropped or changed item, and one line of verdict: `same`, `drift: <what>`, or `not comparable: <why>`. Nothing else. No proposals, no edits to playbooks: the weekly eval does that.
